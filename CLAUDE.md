# FindMeVinyl

A personal Android app (Kotlin, Jetpack Compose) for finding record shops, browsing artist discographies and keeping a want list. It is a hobby project in a public repository, so nothing personal or work-related belongs in this file or in commits.

## How to work on it

- Work test first. For each new behaviour: write the failing test, run it and check it fails for the right reason, write the least code that passes, then run the whole suite.
- Keep steps small. Say briefly what changed and why.
- Run `.\gradlew testDebugUnitTest` after every change (PowerShell on Windows). Roughly 230 tests pass today, and all of them must still pass before moving on.
- Run one class with `.\gradlew testDebugUnitTest --tests "com.nickallport.findmevinyl.shops.OpeningHoursTest"`.
- Test reports are in `app/build/reports/tests/testDebugUnitTest/index.html`.
- Ask before adding a dependency or changing a version. Several versions below were chosen to fix real problems.
- Never stage `local.properties`.
- Keep `README.md` up to date in the same pull request as the change that makes it out of date. Check it whenever a change adds, removes or alters a feature, a setting, a screen, a web service the app calls (the table of data sources, and the privacy section if what is sent changes), how to build or test, or what contributors are asked to do. Say what was checked, or changed, under Changes in the pull request. The README is a public page for people who have not read this file, so write what the app does, not how the code does it, and keep to the plain style used there. Do not put counts that change with every pull request in it (such as the number of tests). When a screen changes a lot, retake its picture in `docs/screenshots` on the emulator with the default settings and no personal data (cover art and artist photos from the app's own sources are fine). The pictures are taken in dark mode (`adb shell cmd uimode night yes`) on the Pixel 8 emulator, 1080x2400, from a fresh install (`pm clear`) with a few artists from MusicBrainz and made-up owned and wanted albums; the sample data was written into the emulator's database with Python's `sqlite3` (pull the three database files, change them, push the main file back with the app stopped), never on the phone.

## Layout

The package root is `com.nickallport.findmevinyl`.

- `musicbrainz`, `nominatim`, `overpass`: Retrofit interfaces, DTOs and mappers for the three public APIs.
- `artist`, `discography`, `favourites`, `wantlist`, `shops`, `export`: logic and view models for each feature.
- `storage`: the Room database, entities and DAOs.
- `location`: the device location lookup.
- `coverart`: the Cover Art Archive URL and `CoverArtLoader`, which downloads album covers.
- `image`: `ImageLoader`, which downloads any image by URL. `CoverArtLoader` is a thin wrapper around it. `wikidata`: the Wikidata API, used to find artist pictures.
- `ui.*`: composables only (`ui.artist`, `ui.discography`, `ui.favourites`, `ui.shops`, `ui.wantlist`, `ui.theme`).

Conventions:

- View models are plain classes, not `androidx.lifecycle.ViewModel`. They sit beside the logic they serve, not under `ui`, and expose suspend functions that return a UI state.
- Screens are stateless composables. A "Route" composable owns the state and takes suspend functions as parameters, so tests can pass fakes and never touch the network.
- `MainActivity` wires everything together. Navigation is a sealed class `Screen` plus a `BackHandler`.
- Composable tests run on the JVM with Robolectric. Network tests use MockWebServer. Pure logic tests use plain JUnit.

- Do not set `ksp.useKSP2=false`. It breaks the build with AGP 9.

## Rules learned the hard way

- DAO methods are `suspend`. Room refuses main-thread queries in the real app, and tests use `allowMainThreadQueries()`. DAO methods return `Long` or `Int` instead of `Unit`.
- When syncing albums from MusicBrainz, use `insertIfNotExists` or `insertAllIfNotExist` (IGNORE) and never `insert` (REPLACE), so a user's owned and wanted flags are not overwritten. Save a whole discography with `insertAllIfNotExist`, which is one transaction. 419 single inserts took 7 seconds on the emulator.
- MusicBrainz returns 25 results unless asked for more, and at most 100 a page. `DiscographyViewModel.discography(artistId)` is a `Flow` that asks for 100 at a time and follows the pages to the `release-group-count`. Each request starts at least 1.1 seconds after the previous one started, and it stops after 10 pages. Each page is saved as it arrives and a state is emitted after it, so the first page shows while the rest load. The list is always built from the saved albums (`loadSaved`), never from a response. An artist opened before starts with its saved albums, before any request. Once as many albums are saved as MusicBrainz lists, the remaining pages are skipped, so reopening an artist is one request. A first page that fails with nothing saved is an `Error`. Any other failure keeps the list and sets `loadError`, so the list is never silently short. Give `MockWebServer.takeRequest` a timeout in these tests.
- Taps on Owned, Want and Save must never reload the discography from MusicBrainz. `DiscographyRoute` calls `loadSaved` and copies the flags onto the albums on screen, album by album, so albums that arrived meanwhile are kept. Before this, every tap re-downloaded every page.
- MusicBrainz sends `"first-release-date": ""` for undated albums. The mapper turns it into null, and `loadSaved` also treats `""` as undated, because rows saved earlier have it. An empty string sorts before every real date.
- The emulator and this machine share one IP, and MusicBrainz limits requests per IP. Repeatedly reopening artists, format lookups and manual probes got "HTTP 503 ... busy" for several minutes. Keep emulator runs against MusicBrainz few, and wait when it answers 503.
- `DiscographyScreen` gives every row and header a key, so the list holds its place as pages add albums above what is on screen. Keep the keys.
- The format filter (`FormatFilter`, `FormatFilterBar`) works on what is stored. An album with `formats == null` has not been looked up, and it stays in the list while a format is chosen, marked "Checking formats…", until its lookup shows whether it matches. An album looked up with no known formats (an empty list) is checked and does not match. Chips and counts come from the albums known so far, so they grow as lookups arrive. The choice is `rememberSaveable` in `DiscographyRoute`, one format at a time.
- `DiscographyRoute` records every format lookup into its own state as it returns (`lookUpFormats`). Without that, the filter, the chips and the counts would be stale, because a row's own result stays inside the row. `refreshSaved` also merges formats from the saved albums, never replacing known formats with none.
- MusicBrainz answers carry `X-RateLimit-Limit` (400 was seen) and `X-RateLimit-Remaining`. Choosing a format while many albums are unchecked starts lookups for the rows on screen, one a second, for as long as it is on screen. Keep emulator sessions with a filter on short.
- `DiscographyViewModel.checkAllFormats` finds the formats of all of an artist's albums from `release?artist={id}&inc=release-groups+media&limit=100`, a hundred releases a request (Genesis is 12 pages, Bob Dylan 24), each page in its own `MusicBrainzThrottle` turn. The formats are saved at the end, in one go, because an album's releases can be on any page. A page answered 429 or 503 is asked for again after the throttle's pause, up to three tries, and any other failure ends the check as `Failed`. The result is `FormatCheckResult` (`Done`, `TooBig`, `Failed`). `DiscographyRoute` runs it once a visit when the discography has settled (not while pages are loading, and a load error does not stop it) and some album has no formats or old ones. Meanwhile the rows wait instead of looking up their own album, and what the check found is brought in with `refreshSaved`. It is a lot of requests for one screen: keep emulator runs against MusicBrainz few, because it makes the shared IP busy (HTTP 503).
- Anything that catches `Exception` around a suspend call must rethrow `CancellationException` first.
- Never hardcode the contact email in the User-Agent. `AppUserAgent.VALUE` is built from `BuildConfig.MUSICBRAINZ_CONTACT_EMAIL`, which comes from `musicbrainz.contact.email` in `local.properties`.
- Nominatim and Overpass are shared public servers. Always send the User-Agent, keep requests few, and keep the Overpass fallback and the `[timeout:25]` setting in the query. The shop search asks `overpass.openstreetmap.fr` first (15 second read timeout) and `overpass-api.de` second (30 seconds), because on 2026-10-16 overpass-api.de took 32 to 45 seconds or timed out in 3 of 4 searches, while the French server answered 12 of 12 in under 4 seconds (kumi.systems failed about half the time, and private.coffee always). `ShopSearchViewModel.queryWithRetry` asks the servers in turn and passes over one that fails, is too slow, or answers HTTP 200 with a `remark` starting "runtime error" (`OverpassResponse.failed`: a timed out query comes back as an empty, successful looking list, which must not be shown as "no shops"). If every server failed with a quick busy answer (429, 502, 503, 504) they are all asked again after a short pause, up to 3 rounds. A timeout or any other failure ends it after one round, because another would take as long again. The last failure is the one shown. The French server refuses a request with a generic User-Agent, so always send `AppUserAgent.VALUE`. Its usage policy could not be read on the server itself, so keep requests few. The query uses `nwr` so shops mapped as buildings are found.
- Nominatim returns latitude and longitude as strings.
- The `Surface` in `MainActivity` uses `Modifier.fillMaxSize().safeDrawingPadding()`. Keep it when editing that file. It sits inside a `Box` with the theme background, so the status and navigation bar areas follow the theme. Without the Box they were flat white and the clock was unreadable in dark mode.
- `OpeningHours` reads a subset of the OpenStreetMap hours syntax. Text it cannot read returns null and the shop row shows the raw text. Rules are read in order and a later rule overrides an earlier one on the days it matches, including public holidays (`PH`): `statusAt(moment, isPublicHoliday)` and `nextOpening(moment, isPublicHoliday)` take the holiday dates, and hours that do not name PH are the same on a holiday. `PH off`, `PH 10:00-14:00`, `Mo-Sa,PH 10:00-18:00` and an additional `Su,PH 15:00-19:30` all work. Without holiday dates, PH rules are ignored, and `OpeningHoursDescriber` adds "(public holidays may differ)". With them, that note goes, and a shop whose hours name PH says "(public holiday today)" on one.
- Public holidays: `PublicHolidayCalendar` gets them from Nager.Date (`date.nager.at/api/v3/PublicHolidays/{year}/{country}`, free, no key). Only a country code and a year are sent, and the user agent is plain `FindMeVinyl/1.0` with no contact address. The answer is kept in the `public_holidays` table (database version 6) for 90 days, per country and year, so it works offline after the first look and costs a request a country and year, not a search. Old rows are used when a new request fails. A 404 (no calendar for the country) is kept too, for 90 days. Only entries of type Public count, and an entry with `counties` only applies when the search's region (`ISO3166-2-lvl4` from Nominatim, such as GB-SCT) is one of them. `datesNear` asks for this year, and next year when the next week reaches into it. The region comes from Nominatim `addressdetails=1` on the town search, its other places and the reverse lookup of a nearby search, so it is the region of the search area, not of each shop. `ShopSearchRoute` loads the dates for the shown result's region and passes `isPublicHoliday` down to `ShopRow`.
- An album can be owned and wanted at once (a worn copy to replace, or a CD owned and the LP wanted). Until database version 17 an owned album was never wanted, and `getWantedAlbums` hid older rows with both flags, so `MIGRATION_16_17` clears `wanted` on every owned album (`Migration17Test`): only wants made after it show on the Wants page. `toggleOwned` no longer touches the want, an owned album still offers `+ Want` on its row (`wanted_toggle`) and on its page (`detail_want_toggle`, "+ Want" or "Wanted" beside the Owned button), `getWantedAlbums` and `markWanted`'s position count include owned albums, and a want is taken off with the Wanted button on the page or the bin on the Wants page.
- Look and feel: the app has its own palette in both light and dark (`ui.theme`), the teal and orange of the icon. Dynamic colour (the wallpaper) is off (`USE_DYNAMIC_COLOR`). `ThemeContrastTest` checks every text and background pair is at least 4.5:1, so change colours there first. The icon teal is too light for text or buttons on white (3.4:1), so light mode uses `TealDeep` for primary.
- Navigation has no menu. `Screen.Home` is the front screen (`HomeScreen`: the big logo and ARTISTS, WANTS and SHOPS buttons). Every other page gets a `Masthead` bar from `MainActivity`, and tapping it goes home. Back goes where `Screen.backTarget()` says: home from any page, from the results back to the Artists page, and from a discography back to where you came from. The Artists page (`Screen.Search`, `ArtistsScreen`) has a search field and the favourite artists. Searching opens `Screen.ArtistResults(query)` (`ArtistResultsRoute`), which searches when it opens unless `SearchResultCache` already holds results for that same query (`artistQuery`), so rotation and coming back from a discography never search again. Only a successful search is cached.
- The logo (`ui.brand.Logo`) is drawn in code with Android's built in `cursive` font, curved along an arc with `drawTextOnPath`. The three button icons (`Glyphs`) are path data, because the Material icons library is not a dependency. Ask before adding one.
- The Shops page (`ShopSearchRoute`) is a search field (the keyboard searches, like the Artists page) and a Near me button. It starts from the last result in `SearchResultCache.shop`, so coming back or rotating costs no request. The first time it opens with nothing kept it searches near you once by itself (`nearbyTried` stops it repeating, and is only set once the search has finished, so a rotation in the middle tries again). That is one Overpass request, which took about 20 seconds on the emulator. After that, only Near me or a typed town searches. A failed nearby search is kept and shown, and Near me tries again.
- Place suggestions while typing in the Shops search use Photon (`photon.komoot.io`, `PhotonApi`, `PlaceSuggester`), because Nominatim's usage policy says search-as-you-type must not be built on its API (read on 2026-10-17: "This is not yet supported by Nominatim and you must not implement such a service on the client side using the API"). Photon's public server has no key and asks only for fair use. It asks for `layer=city&layer=district` only (the `locality` layer brought industrial estates and farms), five results, and the app's User-Agent. The label is the name, county, state and country without repeats ("Newport, Wales, United Kingdom"). `PlaceSuggester` asks for nothing before three letters, keeps each answer in memory by lower case text, and gives no suggestions on a failure (not kept), rethrowing `CancellationException`. `ShopSearchRoute` waits `SUGGESTION_WAIT_MILLIS` (500 ms) after the last letter in a `LaunchedEffect(town)`, which each letter restarts, so an answer for text that was typed over never shows. The list (`place_suggestion_{i}`) replaces the results while it has places. Tapping one (`ShopSearchViewModel.searchSuggestion`) puts its label in the field, remembers it in `pickedText` so it is not suggested for again, closes the keyboard and searches around its position with no Nominatim town lookup; Nominatim is asked once, a reverse lookup, for the region (a failure falls back to Photon's country code). The keyboard's search key still searches the typed text with Nominatim. Photon's typo tolerance is partial: on 2026-10-17 "Caldas da Rai", "Caldas De Rainha" and "Caldas da Reinha" found Caldas da Rainha, and "Caldas De Reinha" (two mistakes) did not. The text typed goes to komoot's server, which the README says. Tests set `suggestPlaces` and `searchSuggestion` on the route, and advance `mainClock` past the wait (a test helper must not be called `wait`, which clashes with `Object.wait`).
- Artist suggestions while typing on the Artists page (`ArtistsScreen(suggestArtists = ...)`, `ArtistSuggester`, `ArtistSuggestions`). The favourites that match (`favouritesMatching`: every word typed is in the name, two letters at least, three at most, the user's order) show at once with no request, marked with a heart and "In your favourites". MusicBrainz suggestions are added after `ARTIST_SUGGESTION_WAIT_MILLIS` (700 ms, longer than the 500 ms for towns because MusicBrainz is limited to a request a second on a shared address) and merged (`merge`: favourites first, no artist twice by id, six in all). The `LaunchedEffect(query)` restarts with each letter, which cancels the wait and any answer on its way. `ArtistSuggester` asks `artist/?query=...&limit=5` through `MusicBrainzThrottle.shared`, so a request waits its turn behind other lookups and costs nothing if it is cancelled while waiting; nothing before three letters; each answer kept in memory by lower case query; a failure or a busy answer gives no suggestions and is not kept. The last word is a prefix ("Joy Divi*") unless the text ends in a space, and characters of the Lucene syntax (`+ - & | ! ( ) { } [ ] ^ \" ~ * ? : \ /`) are replaced by spaces, so AC/DC is "AC DC*" and not a malformed query. "Various Artists" and "[unknown]" (and any artist whose disambiguation starts "Special Purpose Artist") are left out, because a start such as "Va*" brings them in. Tried on 2026-10-17: "Joy Divi*" and "Talk Ta*" put the right band first, and a misspelling such as "Joy Divsion" without a wildcard already found Joy Division. The list is drawn over the favourites (a `Box`), which stay composed beneath it so the grid and its state are kept. Tapping a suggestion opens that artist's discography at once (`artist_suggestion_{i}`), and the keyboard's search key still opens the results page. `MusicBrainzApi.searchArtists` takes an optional `limit` (MusicBrainz sends 25 when it is left out). The results page's own search field has no suggestions. On the emulator the favourite "Joy Division" listed twice because its id there was `grid-test-2`, made up in earlier testing, so the id match failed; real favourites carry MusicBrainz ids. A freshly booted emulator can show "isn't responding" ("Application does not have a focused window") when the app is tapped too early: wait a minute after launch.
- My copies: an owned album lists the copies the user has on its page, for formats and pressings MusicBrainz does not list (see the Copies rule below). Olympia by Bryan Ferry has only CD releases on MusicBrainz (checked 2026-10-17: eight releases, no vinyl, label Virgin), so the app was showing the data correctly and the user's BMG vinyl was missing from it. The copies are kept apart from `formats`, which MusicBrainz fills: `insertAllIfNotExist`, `setFormats` and `setChecked` never touch them, so a discography sync or a lookup cannot overwrite them, and they are added to MusicBrainz's formats, never replacing them. `AlbumUiModel.userFormats` is the formats of the copies and `shownFormats` (both, once each, in order, null while neither is known) is what the format chips, the filter and the visibility rules count; `formats` alone still says whether the album has been looked up (null means ask MusicBrainz), so a copy does not stop the lookups. `FormatLabels` takes `userFormats` and adds them to what it shows. A format hidden by the settings is also left out of the user's formats, with nothing kept in its place; an album is hidden by format only when every format in `shownFormats` is hidden. `AlbumDao.getOwnedOrWanted` also returns an album with copies that is neither owned nor wanted (sold, say). "This is my pressing": the user can choose which of the album's MusicBrainz pressings is their copy. `albums.myPressingId` (the release id) and `albums.myPressingText` (one line, `PressingSummary.oneLine`: date, country by name, label, catalogue number, format, as it was when chosen, so the album can still say which pressing it is when MusicBrainz's list changes) are database version 13 (`MIGRATION_12_13`, schema `13.json`; `Migration13Test` builds a version 12 table with copy details and runs only that step, because `MigrationTest` only goes up from version 10). They are kept apart from `formats` and from the copy details, and sync and lookups never touch them. `DiscographyViewModel.saveMyPressing(albumId, pressing)` stores or, with null, clears them. On the page, `MyCopySection` shows "My pressing: ..." (`my_pressing_text`), a This is my pressing button (`my_pressing_mark`) for the pressing the page is showing (found in `details.pressings` by `pressingId`; not shown while loading, when the shown one is not in the list, or when it is already the chosen one) and Clear my pressing (`my_pressing_clear`). The list of pressings marks the chosen one Mine (`pressing_mine_{id}`, found with `useUnmergedTree = true` since the row is clickable). `AlbumDetailRoute` opens the page on the chosen pressing: once for each load (`triedMine`, reset by Try again), only for an owned album, only when it is in the list and is not the one already shown, with the one request `selectPressing` makes, kept in memory; a failure leaves the first pressing showing without the Couldn't load message. A backup carries both fields, and restore fills them in only when the phone has no chosen pressing, so restoring only adds. (Since database version 20 the formats and the note for each are copies: see the Copies rule.) Limits seen on 2026-10-17: MusicBrainz has no Portuguese pressing of The Joshua Tree (66 releases, 10 official vinyl) and Never Stop is a single with two releases, so for those the user's own formats and note are the way; the pressings list only holds `PressingChooser.candidates`, at most 30, from the first 100 releases of the group.
- Groups of artists (all 3 steps of merging artists; the user's examples are Nick Cave with Nick Cave & The Bad Seeds, Ian Dury with the Blockheads, several Acid Mothers Temple entries on MusicBrainz, Roxy Music with Bryan Ferry). A group is a name of the user's own and a list of MusicBrainz artist ids, in `artist_groups` and `artist_group_members` (database version 14, `MIGRATION_13_14`, schema `14.json`; entities and `ArtistGroupDao` in `storage/ArtistGroupEntity.kt`). MusicBrainz and the albums are never changed, so splitting a group up puts everything back. A group id is `group/` and a UUID (`ArtistGroupViewModel.isGroupId`), so it is never taken for a MusicBrainz id. An artist is in one group at most (`GroupResult.AlreadyInGroup` names the artist and the group), a group needs two different artists (`TooFewMembers`), and the member order matters: the first member is the one whose picture the group uses and whose place in the favourites it takes. A blank name becomes the first member's name. `ArtistGroupViewModel.create`, `update` and `ungroup` check everything before writing and write in one Room transaction (`inTransaction`, which `MainActivity` gives `database.withTransaction`). Members that were favourites keep their `favourite_artists` rows, hidden while they are in a group, so splitting the group brings them back at their own positions (checked on the emulator: Genesis came back third). `FavouritesViewModel(artistDao, groupDao)` lists the artists that are not members and the groups as one list ordered by position then name, and `moveUp`, `moveDown` and `reorder` write a position to the right table by the id. `ArtistDao.minPosition()` counts both tables, so a new favourite still goes first. `FavouriteArtistUiModel` has `isGroup`, `memberIds` and `imageId` (the picture to load: the artist itself, or a group's first member); the list shows "N artists joined" under a group (`favourite_group_note_{id}`). The artist's page has a Join with another artist button (`join_artists_button`, "Edit group" when the artist is in a group, on its own line under Artists and Save) that opens `Screen.JoinArtists` (`JoinArtistsRoute`; saved in `ScreenSaver` as `join`, Back goes to the discography). The page names the group (`join_name`), lists the members with Remove and a make-first arrow, and finds artists to add by typing (`join_search`): matching favourites at once (groups and chosen artists left out), MusicBrainz's after `JOIN_SUGGESTION_WAIT_MILLIS` (700 ms), the same `ArtistSuggester` as the Artists page. Save and Split this group up (`join_save`, `join_ungroup`) both finish on the favourites page. Step 2, the group's own page: a group opens as `Screen.Discography(groupId, groupName)`, the same screen and `DiscographyRoute` as an artist, with the group's id standing in for an artist's id, so Group owned and Group wanted (`GroupingStore` keyed by the group id), the format filter, the settings and the album details all work unchanged. `DiscographyViewModel(groupDao = ...)` expands a group id to its members (`memberIdsOf`): `loadSaved` is the saved albums of every member (an album credited to two members is one row, the first member to save it keeps it, so it is listed once, sorted by date across the members); `discography` (`groupPages`) asks the members one after another, `pageDelayMillis` apart, because MusicBrainz allows a request a second and the paging does not use the shared throttle, shows the saved albums of all members at once, emits the merged saved list after each page, and only the last member's last page says nothing more is coming; a member that fails does not stop the rest (the list keeps what there is with `loadError`, or is an `Error` when nothing at all is saved); `checkAllFormats` checks the members one at a time, each as an artist, leaves out a member whose albums all have formats and statuses that are not stale (`needsCheck`), stops at the first `Failed`, and reports progress as one running count whose total grows as each member's first page says how big it is (so the note can read "20 of 24" and then "32 of 36"); `saveFavourite` does nothing for a group id and `isFavourite` is true for an existing group, so owning or wanting an album on a group page saves no artist. `ArtistGroupViewModel.groupOf` accepts a group id as well as a member's, which is how the Edit group button works on a group page, and the header hides Save there (`showFavourite = false`, `isGroup` on the route), since a group is always kept and is changed with Edit group. `ArtistPictureSource(firstMemberOf = ...)` shows the photo chosen for the group (`artist_user_photos` keyed by the group id, so Change photo on the group page works like an artist's), else the first member's photo, else the first member's web picture, and never asks the web about a group id; `FavouriteArtistUiModel.imageId` is the group's own id, so the favourites show the group's photo too. Checked on the emulator with Bob Dylan and Genesis: the combined list put "Selling England by the Pound" and "The Lamb Lies Down on Broadway" among "Planet Waves" and "Pat Garrett & Billy the Kid" by date. Step 3: the want list, the artist suggestions and backups. `AlbumDao.getWantedAlbums` joins `artist_group_members` and `artist_groups`, and `WantedAlbumRow.artistId`, `artistName` and `artistPosition` are the group's when the album's artist is in one (`COALESCE`), so a group's wanted albums come together under its name in the group's place, in one list across its members, and the share text names the group (`WantListViewModel` is unchanged). An album of an artist that is neither a favourite nor in a group is still left out. A move rewrites every wanted album's position within the group's key. `markWanted` still counts positions per member, so a group's members start with tied positions, which fall back to release date until the first move rewrites them. `ArtistSuggestions.favouritesMatching` finds a group by its own name or by the name of one of its artists (`FavouriteArtistUiModel.memberNames`, in the order of `memberIds`), the words all in one name, and describes it as "Group of N artists", with ", including <artist>" when an artist matched and the group's own name did not. A backup carries `groups` (`BackupGroup`, `BackupGroupMember`: id, name, position, members in order) and the photo chosen for a group, which is an ordinary entry in `photos` keyed by the group id. Restore only adds: a group id already on the phone is left as it is, an id that does not start with `group/` or a group with no id is skipped, an artist already in another group on the phone is left out of the restored one, a group left with fewer than two artists is not restored, a blank name becomes the first member's name, and a group's photo only comes back when the group is on the phone. `BackupFile.VERSION` stays 1 because a field was added and an older app ignores it, which means an older app restoring the file loses the groups. `BackupSummary` and `RestoreResult.Done` have `groups`, and the messages say "2 groups" after the artists. Also found while testing: the Lucene syntax characters in `ArtistSuggester` (`SEARCH_SYNTAX`) had `\/` where a literal backslash was meant, so a backslash typed in the artist search was not taken out. - Genre of an artist or group (part 1 of 2: choosing and keeping it; part 2 is grouping the Artists page by genre, below). MusicBrainz lists genres for an artist with votes, `artist/{id}?inc=genres` (checked 2026-10-17: Nick Cave & The Bad Seeds has alternative rock and post-punk with 11 votes each, punk blues 4, art rock 3, gothic rock 3, and others; an Acid Mothers Temple entry has psychedelic rock, noise rock, space rock and others), `MusicBrainzApi.getArtistGenres`, reusing `MusicBrainzGenreDto`. The genre the user chose is `favourite_artists.genre` or `artist_groups.genre` (database version 15, `MIGRATION_14_15`, schema `15.json`, also the `artist_genres` table), always lower case as MusicBrainz names them (`GenreNames.normalise`: trimmed, one space between words, 40 letters at most, blank is none; `GenreNames.display` puts a capital first, and null is "No genre yet"). `Migration15Test` builds a version 14 database with artists and groups and runs only that step. It uses explicit column lists, because the same `SELECT *` text before and after an `ALTER TABLE` came back from Robolectric's statement cache with the old columns. `ArtistGenreViewModel` (package `genre`) offers the options (`options(id)`: `artist/{id}?inc=genres` in a `MusicBrainzThrottle.shared` turn, kept in `artist_genres` as JSON for 90 days, an artist with none kept as an empty list, the old answer used when asking again fails, null when nothing could be had; the best voted first, 15 at most; a group asks each member one after another and adds the votes, a member that fails leaves the others, and the group's own id is never asked about), and `genreOf` and `setGenre` for an artist id or a group id. The genre can only be kept for a favourite artist (there must be a row) or a group, so the page shows the genre line (`genre_line`, "Genre: Post-punk" or "Genre: none chosen", with `genre_change`) only when the artist is a favourite and not in a group, or is a group (`DiscographyRoute(genreControls = GenreControls(load, options, set))`). The chooser (`GenreSection`, an `AlertDialog`) fetches the options when it opens (spinner `genre_loading`, `genre_failed`, `genre_none_listed`), lists them with their votes (`genre_option_{name}`, "Chosen" on the one chosen), lets the user type their own genre (`genre_custom`, `genre_custom_use`) so an artist with none on MusicBrainz is not stuck, and has `genre_clear` and `genre_cancel`. A backup carries both genres (`BackupArtist.genre`, `BackupGroup.genre`), and restore tidies them, gives a new artist or group the genre, and fills it into one on the phone only when that has none, without counting it as something restored. Part 2, grouping the Artists page by genre: `FavouriteArtistUiModel.genre` (the genre chosen for the artist or group, from `FavouritesViewModel`), a Group by genre chip (`favourites_group_by_genre`) on the same line as the List and Grid chips, after Grid, under the "Your favourites" title (`ArtistsScreenTest` checks the three share a line), and `FavouritesScreen(groupByGenre)`, which works in both the list and the grid. `FavouriteGenreGroups.group` makes the sections: alphabetical by genre, artists with none (null or blank) last as "No genre yet", the user's order kept inside a section, a genre that differs only in capitals or spaces at the ends is the same section; a group of artists is placed by its own genre. A heading (`genre_header_{genre}` or `genre_header_none`) reads "Post-punk (2)" and in the grid spans the whole row (`GridItemSpan(maxLineSpan)`). While grouped the order cannot be changed, because where a picture would go between sections means nothing: there are no move buttons in the list, no drag in the grid (`ArtistGrid` is not used, so no gesture and no Move earlier or later actions), and a line (`favourites_genre_hint`, "Grouped by genre. Turn grouping off to change the order.") takes the place of the drag hint. The user's order is untouched and is there when grouping is off. A tap still opens the artist. The choice is `rememberSaveable` in `ArtistsScreen` and kept in `FavouritesLayoutStore` (`grouped_by_genre`, separate from `grid`), so it survives closing the app, and is not in a backup. The Wants page is not affected, since the want list orders by the artists' positions and the genre is not used there (`WantListViewModelTest` has a test for it). Suggested genre (database version 16, `MIGRATION_15_16`, schema `16.json`, `Migration16Test`): `favourite_artists.autoGenre` and `artist_groups.autoGenre` hold the genre with the most votes, kept apart from the user's `genre`, which always wins. The effective genre is `genre ?: autoGenre` (`FavouritesViewModel`). `ArtistGenreViewModel.fillDefaults(onFound)` runs when the Artists page opens (`ArtistsScreen(fillGenreDefaults)`): in list order (position, then name) it asks `options(id)` for each favourite not in a group and each group that has no `autoGenre`, keeps the top option (ties go alphabetically first, since options are sorted that way), and calls `onFound`, which bumps `genresFound` so `FavouritesRoute(reloadKey)` reads the favourites again. One request a second through the throttle, only once per artist: an empty answer is cached as an empty list and not asked again, a failed one is retried next visit. While it runs and grouping is on, a line (`favourites_genres_finding`) says "Finding genres for your artists…". The artist page shows "Genre: X (suggested)" when only a suggestion exists (`GenreControls.suggested`, `autoGenreOf`), the chooser marks the suggested option "Suggested" while nothing is chosen, and the clear button reads "Use the suggested genre" when there is one. Backups do not carry `autoGenre`: it is found again. A dialog test must not use a tall test window: an `AlertDialog` in `@Config(qualifiers = "w360dp-h2400dp")` (and in `h800dp`) never gets idle under Robolectric ("Compose did not get idle", then out of memory), while the default small window is fine, so `DiscographyRouteGenreTest` uses the default one.

- Copies (database version 20, `MIGRATION_19_20`, `Migration20Test`, schema `20.json`): an owned album has any number of copies, each a format and a note ("part of Mum's collection", "green cover"), several on the same format allowed. They replace the ticked formats (`albums.userFormats`) and the note for each format (`albums.userFormatNotes`) of the "My copy" rules above: those two columns stay in the table and in `AlbumEntity` (deprecated, never read or written), and the migration turned each ticked format into one copy with its note, in the usual order. `album_copies` (`AlbumCopyEntity`: `id`, `albumId`, `format` (a label), `note`, `position`) is read and written through `AlbumDao` (`getCopies`, `getAllCopies`, `insertCopies`, `deleteCopiesExcept`), and `albums.userNote`, the one note about the album, is gone from the app: database version 21 (`MIGRATION_20_21`, `Migration21Test`) turned every album note into one more copy on LP with the note as its description (after the copies it has), cleared the column, and the column stays unused (deprecated in `AlbumEntity`). `DiscographyViewModel.saveCopies(albumId, copies)` keeps at most `MAX_COPIES` (20), drops a copy whose format is not a label, trims and cuts notes to `MAX_NOTE_LENGTH`, stores a blank note as null, and replaces the old copies by inserting the new ones first and then deleting the rest, so an interruption leaves too many, never too few. A want on a format goes when a copy is on that format. `AlbumUiModel.copies` (`AlbumCopy(format, note)`) is what the screens use, and `userFormats` stays as the formats of the copies, each once in the usual order, so the format filter, the chips and the settings rules work as before; `loadSaved` reads every copy in one query. On a discography row (`AlbumRow`) the order is title, artist, the formats line ("LP · CD", MusicBrainz's and the copies'), one line per copy (`album_copy_{i}`, "LP: Green cover", or just "CD" with no description, cut at two lines) and then the "Wanted" or "Wanted on CD" label (`album_wanted_label`). `MyCopySection` is "My copies": a summary line per copy ("LP: green cover") and an editor with, for each copy, a format chosen from the chips (`my_copy_{i}_format_{label}`), a note (`my_copy_{i}_note`) and Remove this copy (`my_copy_{i}_remove`), then Add a copy (`my_copy_add`, a new copy starts on LP). With no copies yet the button on the page says "Add a copy" and the editor opens with one copy ready (LP chosen, note empty), so the formats are there to choose from; saving it at once keeps one LP copy with no description, Save and Cancel. The copies being edited are kept over a rotation as one text (`CopyDrafts`). A backup carries `BackupAlbum.copies` (`BackupCopy(format, note)`); a file from an earlier version has `userFormats` and `userFormatNotes` instead, which restore turns into copies (`FormatNotes.decode`, kept for this and for the migrations), and a `userNote`, which restore adds as one more copy on LP, as the migration did. Restore adds copies only when the album has none on the phone, and keeps only labels.

- Want on a format: a wanted album can be wanted on one format, such as the LP of an album owned on CD. `albums.wantFormat` (a label from `ReleaseFormats.displayOrder`, null for any format; database version 18, `MIGRATION_17_18`, `Migration18Test`) is kept while the album is wanted: `AlbumDao.setWanted(false)` and `clearWantedForArtist` set it to null, and `DiscographyViewModel.saveWantFormat` ignores an album that is not wanted and anything that is not a label. `saveCopies` takes the want off (`setWanted(false)`, so the format goes too) when one of the copies is now on the format it was wanted on, and leaves it alone otherwise. The album's page shows a "Want it on" row of chips while it is wanted (`want_format_any`, `want_format_{label}`, `AlbumDetailScreen(onSetWantFormat)`, `AlbumDetailRoute(saveWantFormat)`), the discography row says "Wanted on LP" (`album_wanted_label`), the Wants page shows "on LP" under the title (`want_format_{albumId}`) and the share text says "- Desire (on LP)". - A-Z on the Artists page: an A-Z chip (`favourites_sort_az`) after Group by genre sorts the favourites by name, ignoring capitals (`String.CASE_INSENSITIVE_ORDER`, nothing cleverer: "The Smiths" is under T), in the list and the grid. `ArtistsScreen(startSortedAz, onSortedAzChange)` holds it in `rememberSaveable`, `MainActivity` keeps it in `FavouritesLayoutStore` (`sorted_az`, apart from `grid` and `grouped_by_genre`, not in a backup), and `FavouritesRoute(sortAz)` and `FavouritesScreen(sortAz)` take it. While it is on the order cannot be changed, as when grouped by genre: no move buttons, no drag in the grid, and a line (`favourites_az_hint`, "Sorted A to Z. With Group by genre on too, each genre section is in A to Z order and the one hint (`favourites_genre_hint`) says both. - Settings: the user chooses what to hide on a Settings page (`Screen.Settings`, `SettingsScreen`), reached from the quiet Settings button under the three big ones on the front screen. `Settings` is a data class of yes-or-no values, all of the form "hide X", with the user's own defaults (hide Digital, bootlegs, promos, unknown status releases and charity shops; the rest off). `SettingsStore` keeps them in the app's `settings` preferences file, one boolean each, and saves every one, even at its default, so a choice the user made survives a later change of default. A value of the wrong kind reads as the default. `AppSettings` holds the current `Settings` as a `StateFlow` and saves on `update` or `set`; `MainActivity` makes one and reads it with `collectAsState()`. A row of the page is a `toggleable` Row with the tag `setting_{name}`, and it passes on the whole `Settings` with that one changed. Albums the user owns or wants are never hidden by a setting, so they cannot lose track of them. Hiding charity shops (`hideCharityShops`, on by default) and second-hand shops (`hideSecondHandShops`, off by default, because some second-hand record shops are tagged `shop=second_hand` on OpenStreetMap) is done in `ShopSearchRoute` on what is shown: the kept result in `SearchResultCache` still has them, so switching a setting needs no new search, and a note under the place name says how many are hidden (`hidden_shops_note`) and goes to Settings. The note names the kind when only one kind was left out ("3 charity shops", "1 second-hand shop") and says "shops" when it was both (`hiddenNoun`). `HomeScreenTest` and `SettingsScreenTest` run in a taller test window, because the page does not fit the small default one.
- What the settings leave out of a discography is decided by `DiscographyVisibility.apply(grouped, settings)`, on what is shown, so changing a setting needs no new load. An album you own or want is never hidden. Otherwise it is hidden when its kind is hidden (live albums, compilations, singles, other releases; studio albums and EPs cannot be hidden), or when every format it is known to have come out on is hidden. LP, CD, 12", 7", MC (cassette) and Digital can be hidden (the label constants are in `ReleaseFormats`), 10" cannot. A hidden format is also taken out of the album's `formats`, so the row, the format chips and their counts do not show it (`displayFormats`, which keeps them all when that would leave none, for an owned album that is only on a hidden format). An album whose formats are not known yet, or are known to be none, is shown. `DiscographyRoute` takes `settings` (default `Settings.ShowEverything`, so tests are not about the settings), keeps the raw albums for taps and lookups, and builds the chips and the list from what is left. A note under the chips says how many albums were left out (`hidden_albums_note`) and goes to Settings. A lookup shows its formats through `displayFormats` too. `DiscographyRouteSettingsTest` runs in a tall test window.
- Hiding by release status (`hideBootlegs`, `hidePromos`, `hideUnknownStatus`) uses `albums.statuses` (database version 8, `MIGRATION_7_8`), the statuses of an album's releases as `ReleaseStatuses` tokens (`Official`, `Promotion`, `Bootleg`, `Other`, which covers Withdrawn, Cancelled, Pseudo-Release and no status), each once, sorted, joined with `|`. Null means never looked up, empty means none listed. Both the whole-artist check (`FormatCheckProgress.statusesByAlbum`, saved with the formats by `AlbumDao.setChecked`) and the per-album lookup (`loadFormats`) save them, so `setChecked` is the way to save a look at an album's releases. An album is hidden by status only when its statuses are known and non-empty, none is `Official`, and every one is of a hidden kind. Null or empty statuses leave it shown, as owned and wanted albums are. An album hidden by several rules is counted once in `hiddenCount`. `DiscographyRoute` starts the whole-artist check also when some album has `statuses == null`, so each artist saved before version 8 is checked once more (12 to 24 requests for the big ones), and calls `refreshSaved()` after a per-row lookup to bring the saved statuses onto the screen. Albums that none of the artist's releases belong to keep null statuses, so they ask for the check again on every visit, as they already did for formats.
- Tapping a shop opens its own page (`Screen.ShopDetail(shop, region)`, `ShopDetailRoute`, `ShopDetailScreen`) instead of going straight to a map. Back goes to the Shops page, whose kept result (`SearchResultCache.shop`) is still there, so it costs no request. `ScreenSaver` keeps the page by writing the whole `Shop` as JSON (Gson) and the region as two strings, so it survives a rotation and the process being killed. The page shows what OpenStreetMap has and leaves out what it has not: name and kind (with ", second-hand only" for `second_hand=only`, which a `shop=music` shop can have), whether it is open now, the address, phone, website and email, the hours of each day (`OpeningHours.hoursText`, with today in bold, and `publicHolidayText` as a "Public holidays" line), and an Open in map button (`openInMaps`, a `geo:` link). Hours that cannot be read are shown as written (`hours_raw`). The route looks up the public holidays of the shop's region like the list does. `Shop` carries `address` (`ShopAddress`: street, house number, postcode, city, country), `phone`, `website`, `email` and `secondHandOnly`, read by `OverpassShopMapper` from `addr:*`, `phone` or `contact:phone`, `website` or `contact:website`, and `email` or `contact:email`, blank values counting as missing. `ShopAddress.lines(fallbackCountry)` lays an address out the way the country does it: number before the street in GB, IE, US, CA, AU, NZ, ZA and FR, the postcode after the town in all of those but FR, otherwise street first and postcode first. The country is the one on the address, or the country of the search when the address has none (most do not), or neither, with the street first. The text comes from volunteers, so only what `WebLink.normalise` (http and https only, a bare host gets https), `PhoneLink.dialUri` (digits and a leading plus, at least five digits, first number only) and `EmailLink.mailUri` accept is ever handed to another app; anything else is shown as plain text. `MainActivity.openLink` starts the dialler, browser or mail app and shows a short message if there is none. OpenStreetMap has no photos of shops (none of 53 record shops in Lisbon, London and Dundee had `image` or `wikimedia_commons`).
- Favourite shops: a heart button on a shop's page (`shop_detail_favourite`, "Add to favourites" / "Favourite") keeps the shop, and tapping it again lets it go with no question. They are in the `favourite_shops` table (database version 9, `MIGRATION_8_9`, entity `FavouriteShopEntity`, `FavouriteShopDao`) with a snapshot of everything known about the shop when it was kept (name, kind, position, hours, address in parts, phone, website, email, second-hand only, and the region for public holidays), so the list and each shop's page work with no search and no network. `FavouriteShopsViewModel` adds (keeping again updates the snapshot), removes, reads the ids and lists the shops by town then name, ignoring case, shops with no town last. The id is the OpenStreetMap element as `node/123`, `way/123` or `relation/123` (`OverpassShopMapper`), because the numbers of the three kinds overlap. A Favourites button (`shops_favourites_button`) sits next to Near me on the Shops page and opens `Screen.FavouriteShops` (`FavouriteShopsRoute`, `FavouriteShopsScreen`): the shops under a heading for their town (`favourite_shops_town_{town}`, "Other places" when there is none), each a `ShopRow` that opens the shop's page. `Screen.ShopDetail` carries `backTo` (the Shops page, or the favourites), so Back goes where the user came from, and an older saved state with no `backTo` goes to the Shops page. A favourite in the search results has a small orange heart (`shop_favourite_heart`): `MainActivity` reads the ids each time the Shops page opens. Favourite shops are in a backup (`BackupFile.shops`, `BackupShop`) and restore only adds the ones not on the phone yet, skipping any with no id or a position outside the map; an unknown kind becomes a record shop.
- Adding a shop that OpenStreetMap does not have (`Screen.AddShop(sharedText)`, `AddShopRoute`, `AddShopScreen`), reached from the Add a shop button on the favourite shops page (`favourite_shops_add`) or by sharing from Google Maps into the app (an `ACTION_SEND` `text/plain` filter in the manifest, `launchMode="singleTask"` so a running app gets `onNewIntent`; `MainActivity.incomingShare` is turned into the screen by a `LaunchedEffect`; the app's own want list chooser excludes the app with `EXTRA_EXCLUDE_COMPONENTS`). What Google Maps gives has NO position in it: the Maps app shares the name, the address on the next line and a short link, and following the link (`MapsLinkResolver`: https only, only Google Maps hosts at every hop (`SharedPlaceParser.isMapsLink`), at most 5 hops read from the headers without loading the page, no cookies, redirects elsewhere end it) leads to `google.com/maps/place/Name,+Address/data=...`, again with no coordinates. A `share.google` link leads to a Google search page and is not followed. `SharedPlaceParser.parse` reads the shared text (name, address, link, or a pasted pair like `39.4036, -9.1349`), `fromPlaceUrl` reads a followed link (and a `consent.google.com` page's `continue` link). The position then comes from, in this order: coordinates pasted (exact), `ShopPositionFinder` (Nominatim, whole address first, then the town with the postcode taken off, a second apart, so at most two requests; the town is `approximate`), or the phone's position (`Use my position`, which asks for location permission). Nominatim usually knows the street, not the house (it matched Silver Tentacle's street to a few hundred metres), so the status says the position may be a little off. A shop added by hand has the id `custom/{uuid}` (`Shop.isCustom`), is saved at once as a favourite, `approximatePosition` and `mapQuery` (database version 10, `MIGRATION_9_10`) say when its position is only the town's and what text to search a map app for: `MapLinkBuilder.geoUri` then opens `geo:lat,lon?q=name, address`, so Google Maps finds the shop itself even when the position is rough. `ShopAddress.fromText` splits the one-line address into street, postcode and town so the shop sorts under its town. Shops added by hand are also listed in a search for the place they are near (`ShopSearchViewModel` `customShops`, within the search radius, once each). Opening hours cannot come from a Google Maps link (the share has only the name, the address and the link), so they are typed. `FriendlyHours.toOsm` turns plain wording into the form `OpeningHours` reads: "Mon-Sat 10-7; Sun closed" becomes "Mo-Sa 10:00-19:00; Su off". It accepts short and long day names, `to`, `&`, `weekdays`, `weekends`, `daily`, no days at all (every day), 24 hour times, am and pm, minutes with a dot, two spells in a day, and an end time smaller than the start with no am or pm taken as the afternoon (10-7 is 19:00). Text that is already in the OpenStreetMap form is kept as it is, and a rule that cannot be read makes the whole text unreadable (null). The form shows "Understood as: ..." under the field when the result differs from what was typed, a note when it is not understood (it is then kept as written and the shop does not say whether it is open), and nothing when it is already in the OpenStreetMap form. A shop added by hand has an Edit this shop button on its page (`shop_detail_edit`, only for `Shop.isCustom`), which opens the same page (`Screen.AddShop(null, editing = shop)`, `AddShopRoute(editing = ...)`, `AddShopForm.from(shop)`, `ShopAddress.toText`) with the details filled in, "Edit shop" as its title and "Save changes" on the button. Saving keeps the id, the email and anything else that is not on the form (`base.copy(...)`), and replaces the saved favourite. The position is kept unless the user pastes another or uses their own. A shop added from a Google Maps link keeps that link (`Shop.mapsLink`, database version 11, `MIGRATION_10_11`, `AddShopForm.mapsLink`, included in a backup): only a link that `SharedPlaceParser.isMapsLink` accepts is kept, and it is checked again when it is shown and when a backup is restored. The shop's page then has a View on Google Maps button (`shop_detail_google_maps`, `MainActivity.openLink` with `ACTION_VIEW`), which opens the place on Google's own page with the hours, photos and reviews that cannot be read into the app: the share has only the name, the address and the link, the Places service needs a billing account and a key, and reading Google's page is against its terms. Reading another link while editing replaces the kept one. Test names that open a database file must stay short (about 90 characters at most): a 107 character name made Robolectric's temporary folder too long for Windows and the test failed with "unable to open database file".

- Album covers come from the Cover Art Archive at `coverartarchive.org/release-group/{id}/front-250`, using the MusicBrainz release group id the discography already has. - Release formats are fetched per album from `release?release-group={id}&inc=media&limit=100` and stored in `albums.formats` as MusicBrainz's raw names joined with `|` (a comma will not do, some names contain one), with `formatsCheckedAt`. Null means never fetched, an empty string means fetched and none known. `ReleaseFormats` turns the names into the labels (LP, 12", 10", 7", CD, MC, Digital), so the rules can change without fetching again. Formats are looked up only for rows on screen, and refreshed after 30 days. Every lookup goes through `MusicBrainzThrottle.shared`: one at a time, 1.1 seconds apart, a pause after a 429 or 503. A started lookup saves its result inside the throttle block, so cancelling the row does not lose it.
- Every change to a Room entity needs a version bump and a `Migration` in `storage/Migrations.kt`, never a destructive fallback, because it would delete a user's owned and wanted flags. Room writes each version's schema to `app/schemas`, and those files are committed. `MigrationTest` builds the old database from SQL, fills it with data, and opens it with the current database.
- Artist pictures on the search results come from Wikimedia Commons, found through an exact chain and never by name: MusicBrainz `artist/{id}?inc=url-rels` gives the Wikidata item, Wikidata `wbgetclaims` property P18 gives the file, and the address is `commons.wikimedia.org/wiki/Special:FilePath/{file}?width=120`. If Wikidata has no picture, MusicBrainz's own "image" link to a Commons file is used. `ArtistImageViewModel.loadImageUrl` keeps the result in the `artist_images` table (a null address means "checked, no picture", and is kept too), looks again after 90 days, and keeps nothing on a failure. Finding and saving run inside one `MusicBrainzThrottle` turn, so a cancelled row cannot lose a result. `ImageLoader.shared` downloads the picture. The search results show "Artist photos: Wikimedia Commons" while a picture is on screen, because Commons asks for credit. Do not match artists to pictures by name (Deezer put the wrong "Genesis" first).
- `SquareImage` is the one composable for the 56dp square with the record placeholder, used for album covers (`CoverImage`) and artist pictures (`ArtistImage`).
- `CoverArtLoaderTest` uses `@GraphicsMode(GraphicsMode.Mode.NATIVE)`. In the default mode Robolectric returns a fake bitmap for bytes that are not an image, where a device returns null. Give `MockWebServer.takeRequest` a timeout, because it waits forever when no request is made.
- Restore tests use `runComposeUiTest` with `StateRestorationTester(this)` and `emulateSaveAndRestore()`, under `@OptIn(ExperimentalTestApi::class)`. It takes a `ComposeUiTest`, not a rule.

- Tapping an album row opens `Screen.AlbumDetail` (`AlbumDetailRoute`, `AlbumDetailScreen`); Back goes to the discography it came from, and `ScreenSaver` keeps the whole chain. The row has an Owned pill (`owned_toggle`, "+ Owned" when not owned) and a `+ Want` pill. They no longer share the row's tap, so a test that toggles owned taps `owned_toggle`, not `album_row`.
- The detail page shows one pressing at a time, a rating, and a list of the album's pressings. `PressingChooser.candidates` gives the pressings: the official vinyl releases, earliest first; without vinyl the official releases of any format; without anything official every release. Undated releases come last. `ReleaseDates.sortKey` sorts a date known to the month or day before a bare year of the same year ("1970-10" before "1970", then "1971"), and is used for pressings, the discography and the want list's fallback order. The first candidate is the one the page opens on, and at most 30 are kept. `AlbumDetailsViewModel.load` makes three requests in one `MusicBrainzThrottle` turn, each in its own slot (`awaitNextSlot()`): the release list with `inc=media+labels` (the pressings), `release/{id}?inc=recordings+labels+release-groups+genres` for the first pressing's tracks, and `release-group/{id}?inc=ratings` for the rating. Details are stored in `album_details` (database version 4) as JSON (`AlbumDetailsJson`, which carries a `version`, now 3: a row with no version or another one reads as missing and is fetched again, so raise it when the stored layout or the order of the pressings changes), looked up again after 90 days. A failure of any request returns null and stores nothing. An album with no releases is stored as empty, so it is not asked about again for 90 days. Tapping another pressing calls `selectPressing`: one request (`inc=recordings+labels`), kept only in memory for the run of the app, shown with the album's own genres, pressings and rating (`AlbumDetails.withPressing`). The choice is not stored, so the page opens on the first pressing again. The `inc` lists are sent with `encoded = true`, because MusicBrainz reads an encoded plus sign as a literal plus.
- `TrackSections` groups tracks into "Side A/B" when track numbers are A1, B1 and so on, otherwise by disc. `CountryNames` turns MusicBrainz country codes into names (XW is Worldwide, XE is Europe). The large cover is `CoverArtLoader.loadLarge` (`front-500`), and `SquareImage` takes a `size`.

- The user orders things by hand, and only the Artists page and the Wants page show that order. `favourite_artists.position` orders the favourite artists, and `albums.wantPosition` orders a wanted album among its artist's wanted albums (database version 5). The want list and the share text are artists by `position`, then albums by `wantPosition`. Equal positions are ties: all rows start at 0 after the upgrade, and ties fall back to the old order (artists by name, albums by release date with undated last, then title). A move (`FavouritesViewModel` and `WantListViewModel` `moveUp`/`moveDown`, using `Reorder.swapped`) rewrites every position in that list as 0, 1, 2 and so on, so ties disappear on the first move. A new favourite (`saveFavourite`) goes first, one place before the lowest position (`ArtistDao.minPosition`, so positions can be negative until the next move rewrites them as 0, 1, 2), a newly wanted album (`AlbumDao.markWanted`) goes last, and saving a favourite that already exists must not change its position (`toggleWanted` saves the artist every time, and `toggleOwned` does when it marks an album owned, so both taps on a discography make the artist a favourite). The discography ignores `wantPosition` and stays in release order. `MoveButtons` is the shared up/down arrow pair, with its own tags: `favourite_up_{id}`, `favourite_down_{id}`, `want_up_{albumId}`, `want_down_{albumId}`.
- Sharing the want list asks first. The Share button on the Wants page opens a dialog (`share_dialog`) with an optional message (`share_intro`), a choice of how many albums (`share_limit_10`, `_20`, `_30`, `_50` and `share_limit_all`, only the ones smaller than the list, and none at all for a list of 10 or fewer) and a summary line (`share_summary`: "Sharing all 28 albums" or "Sharing the top 10 of 28 albums"), with Share (`share_confirm`) and Cancel (`share_cancel`). The choices are `rememberSaveable`, so they are kept over a rotation and for the next time the dialog opens in the same run of the app, but not after the app is closed. They go up as `ShareOptions(intro, limit)` and `WantListRoute` passes them to `exportText`. `WantListFormatter.format(items, intro, limit)` puts the trimmed message above the header with a blank line, and takes the first `limit` albums in the user's own order (artists by position, then albums by want position), which can stop in the middle of an artist. A limit that is not positive or is as big as the list shares everything, and a shorter one makes the header "My vinyl want list (top 10 of 28):".
- The favourite artists on the Artists page can be shown as a list (the default: picture, name and move buttons) or as a grid of pictures only, to fit many more on a screen. Two chips beside "Your favourites" switch between them (`favourites_view_list`, `favourites_view_grid`). `ArtistsScreen` holds the choice in `rememberSaveable`, starting from `startInGrid` and reporting each switch through `onGridChange`, and `MainActivity` keeps it in `FavouritesLayoutStore` (the `favourites_layout` preferences file, key `grid`), so it survives closing the app. It is a choice of look and is not in a backup. `FavouritesScreen(grid = true)` draws a `LazyVerticalGrid` with tiles at least 76 dp wide (four across on a 360 dp phone), each tile a square `ArtistImage(fillSize = true)` with the tag `favourite_artist_{id}` and the artist's name as its content description. Every tile shows the artist's name along the bottom on a dark bar, on one line, cut with an ellipsis when long ("Nick Cave & t…"), so bands can be told apart even with good photos. Robolectric measures text as zero width, so the cut cannot be tested there and was checked on the emulator. A quick touch opens the artist (the tile's `clickable`). Holding a tile for the long press time lifts it (bigger, on top), and dragging on moves it through the grid with the others making room (`animateItem`). The gesture is one `pointerInput` on the whole `LazyVerticalGrid` in `ArtistGrid`, not on the tiles, because a tile that has moved cannot follow a finger that began on it. It waits for the long press itself in the Initial pass (`awaitLongPressOrCancellation` was cancelled at once, because the tile's `clickable` takes the press), and once lifted it consumes the events in that pass so the grid does not scroll and the release is not a tap. Lifting the finger calls `onReorder(ids)` (`FavouritesViewModel.reorder`, which writes positions 0..n-1 and leaves out unknown ids), and the route reads the list again. A drag ended another way, or ending where it began, restores the order. A finger within 56 dp of the top or bottom edge scrolls the grid while held. A tile also has TalkBack actions Move earlier and Move later. The tiles in the test use `mainClock.advanceTimeBy` after `down` to pass the long press time. The grid's `order` state is made once and is not keyed on the list: the gesture block is set up once and keeps the state it first saw, so a state made anew for each reloaded list (after every drop the route reads the list again) left the gesture moving a copy nobody saw, and the other pictures stopped making room from the second drag on while the drop still worked. A `LaunchedEffect(artists)` copies a reloaded list in, never while a picture is held. `FavouritesGridGestureTest` has a second drag after a reload for this. A line (`favourites_grid_hint`) says how to move a picture. The tiles use the 120 px pictures that the list uses, so they are slightly soft on a large phone.
- Owned and wanted look different on a discography row (`AlbumRow`): owned is the teal card (`primaryContainer`), wanted is the orange card (`secondaryContainer`) with a "Wanted" label, and an album that is neither has the plain card. Once an album is wanted, its `+ Want` pill goes: it comes off the list with the bin on the Wants page (`WantListViewModel.remove`, asked first with a confirmation, `want_remove_{albumId}`, `want_remove_confirm`, `want_remove_cancel`), or with the Wanted button on the album's details page. The album stays, as not wanted. An album that is owned and wanted keeps the teal owned card and shows a "Wanted" label (`album_wanted_label`) under its formats, with no `+ Want` pill. `ThemeContrastTest` checks the text on both card colours.
- The discography header (`DiscographyHeader`) is the artist's name with a line under it: Artists (`artists_button`, goes to `Screen.Search`, the favourites page, whatever page you came from) and Save or Saved. Two chips lead the format chip row, Group owned (`group_owned_toggle`) and Group wanted (`group_wanted_toggle`) (`FormatFilterBar` with `grouping`). A `Grouping` (`discography/Grouping.kt`) is `owned`, `wanted` and `wantedFirst`: the order of the two sections is its own value, kept while a group is switched off. `DiscographyRoute` keeps it as text (`GroupingText`, comma separated words `owned`, `wanted`, `wantedFirst`) in `rememberSaveable`, so it survives a rotation, and it is kept for each artist across visits and app restarts: `GroupingStore` (the file is still called `owned_first`, so artists that had the old Owned first switch on keep it: the old value was a true boolean, which reads as owned; artists with no group on are removed) is read by `MainActivity` into `startWithGrouping` and written through `onGroupingChange`. With a group on, `DiscographyScreen` takes those albums out of their categories into an Owned section (`owned_section_header`) and a Wanted section (`wanted_section_header`) at the top, each in the order of the categories, Owned first unless `wantedFirst`, and a category left empty disappears. An album that is both is in the Owned section when Group owned is on, and in the Wanted section when only Group wanted is on, never in both. When both sections have albums, the second has an up arrow (`group_first_owned`, `group_first_wanted`) that puts it first (`onWantedFirstChange`); with one section empty or one group off there is no arrow. A chosen format narrows both sections too, and the format chips still count every album. Changing the grouping or its order scrolls the list to the top, because the list keeps its place by item and the new section would otherwise sit above the screen. `DiscographyRouteTest` and `DiscographyScreenTest` run in a tall test window (`@Config(qualifiers = "w360dp-h2400dp")`), because the header and chips leave a LazyColumn no room in the default small one and its rows are never composed. A scroll test needs the small window, so it is in its own class (`DiscographyScreenScrollTest`).
- The user can choose their own photo for an artist, because some pictures from Wikimedia Commons are poor or missing. The artist's picture sits beside the name in the discography header, with a caption that says Add photo or Change photo (`change_photo`), and tapping it opens the system photo picker (`ActivityResultContracts.PickVisualMedia`, no permission needed). `ArtistPhotoViewModel` keeps the photo: `PhotoScaler` scales it to at most 600 px on its longest side as a JPEG (turned upright from the EXIF note, since decoding ignores that, and on white if it was transparent), `ArtistPhotoStore` writes it to `filesDir/artist_photos/{artistId}-{time}.jpg`, and the `artist_user_photos` table (database version 7) says which file belongs to which artist. Every photo gets a new file name, so a picture shown from the old file is not mistaken for the new, and the old file is deleted. The file name is made safe from the artist id. The Wikimedia picture is never touched. There is no way back to it from the app, on purpose: choosing a photo was a decision (the option "Use original photo" was removed), so a photo can only be replaced by another. `ArtistPictureSource` decides what is shown everywhere (header, favourites, search results): the user's photo first, and then the web is not asked at all. A photo over 30 MB is refused (`LimitedReader`), as is anything that is not a picture, with a short message. The "Artist photos: Wikimedia Commons" credit line still shows when only a user photo is on screen.

- Backup and restore (`backup` package, `BackupViewModel`) saves what the user chose and MusicBrainz cannot give back. A backup is a zip: `backup.json` (`BackupFile`: `app` "FindMeVinyl", `version` 1, favourite artists with `position`, the albums that are owned or wanted with `wantPosition`, which photo belongs to which artist, the favourite shops, and the `Settings`) and `photos/{fileName}`. Other albums are left out, because the discography loads them again; formats, statuses, covers and album details are fetched again too. Raise `BackupFile.VERSION` only when a field changes meaning. `restore` only adds: it reads and checks the whole zip first (a file that is not a zip, has no `backup.json`, is from another app, or has a newer version is `RestoreResult.Failed` and nothing changes), then merges in one Room transaction. An owned flag is never cleared, an album owned in the file is made owned and one wanted in the file is made wanted, each separately (an album can be both), an artist already on the phone is kept as it is (name and position), an album already wanted keeps its place, a photo already chosen for the artist is kept, and the settings in the file replace the current ones. Restoring the same file again changes nothing. The photo name inside the file is never used as a path: the file gets a name made from the artist id (`safeFileName`) and the time, a photo must decode as a picture and be at most 5 MB, `backup.json` at most 20 MB, and the zip at most 5000 entries. The result counts only what was added.

- The Settings page has a Your data section (`SettingsRoute`, which `MainActivity` shows instead of `SettingsScreen` alone) with Back up (`backup_button`) and Restore (`restore_button`). The route owns the last message (`data_message`, `rememberSaveable`, so it survives a rotation) and a busy flag that disables both buttons while one runs. `MainActivity` does the file part with the system pickers, which need no permission: `ActivityResultContracts.CreateDocument("application/zip")` suggests `FindMeVinyl-backup-{date}.zip` and writes with mode `wt` so an older file is truncated, and `OpenDocument` is offered `*/*` because file apps do not agree on what a zip is called (a wrong file is refused by `BackupViewModel`). Both return null when the user backs out, and then nothing is said. The wording is in `BackupMessages` (counts only what was added). The pickers use a `CompletableDeferred` like the photo picker, so a rotation while the picker is open loses the result: the user taps again. Checked on the emulator: a backup was written, and a restore of a changed copy added one artist and one album and turned a setting on.
- Dependabot (`.github/dependabot.yml`) checks Gradle libraries and GitHub Actions monthly, in one grouped PR. It never offers Kotlin, KSP, AGP, the Compose BOM or the Gradle wrapper: a KSP patch update (2.2.10-2.0.2 to 2.2.21-2.0.5) broke the build with AGP 9, so those are moved by hand, with a build and an emulator check. For Room, Robolectric, OkHttp and Retrofit it offers patch updates only, because those versions were chosen to fix real problems. Treat its PRs like any other: the `test` check must pass, and ask before taking a version change.

## Running the app

- The emulator on this machine needs Graphics set to Software - GLES 2.0, or the screen stays black.
- Killing the emulator (`adb emu kill`) loses the last writes: on 2026-10-17 a value cleared in the app and confirmed in the database by `run-as` was back after the kill and a reboot, and copy details saved a minute before a kill were gone. The app was fine, the emulator had not flushed its disk. Wait a few minutes after a change before killing it if the change has to be there next time, and do not read a missing value after a reboot as a bug without checking the database first (`adb exec-out run-as com.nickallport.findmevinyl cat databases/find-me-vinyl-db` and its `-wal` and `-shm` files, then open the copy with Python's `sqlite3`; the phone's own database can be read the same way).
- Fake the GPS position with `adb emu geo fix <longitude> <latitude>` (longitude first). It resets when the emulator restarts.

## Known gaps

- Hiding bootlegs, promos and unknown status relies on the whole-artist check. An artist with more than 60 pages of releases is not checked that way, so only albums that have been looked up one by one (rows on screen) are hidden by status, and only from the next visit if the screen already showed them. MusicBrainz's release status is the only signal, so a bootleg with the wrong status stays shown.
- Search results are kept in memory only (`SearchResultCache.shared`). Rotation keeps them, but if Android kills the process the user gets the right screen and typed text back and has to search again. A search that is loading during a rotation is not resumed.
- The formats of an album are those of every release in its release group, so a later CD reissue of a record that was only ever on vinyl shows CD. Only the first 100 releases of a group are read. Format names that are not shown (DVD, SACD layers and so on) are ignored. New rows fill in at about one album a second, and the discography paging does not use the shared throttle.
- Artist pictures show on the search results and the favourites list (both use `ArtistImage` and `PhotoCredit`). A first search costs about two requests per visible artist (MusicBrainz and Wikidata), one a second, and nothing after that for 90 days. Coverage was only measured on well-known artists, so obscure artists may often have none. The picture is a photo cropped to a square, so some faces are cut off. The user cannot crop a chosen photo, and the screens centre-crop it into a square, so a tall photo loses its top and bottom. The photos are in the app's own folder, so they are lost with the app's data, unless the user has made a backup from Settings (Your data), which includes them.
- The detail page lists at most 30 pressings, and the list holds only the ones `PressingChooser.candidates` picks, so a non-vinyl pressing of a record that also came on vinyl is not listed. The rating is the average of MusicBrainz users' votes for the album, not for a pressing. A chosen pressing is not remembered. Opening an album not seen before costs three MusicBrainz requests. The album details do not open from the Wants list, on purpose: the Wants list is a list to share.
- Covers are cached in memory only. archive.org sends no cache headers, and every album costs a redirect request per run of the app. The cover is the release group's usual front cover, not the cover of a vinyl pressing.
- Try again after a failed page loads the discography again from page 1. A first page that fails with nothing saved shows only the error, with no Try again button. A list is built from every saved album, so an album MusicBrainz later removes from a discography still shows.
- The format filter is complete only after the check of the whole artist has finished (a line under the chips shows its progress). It starts by itself once a discography has settled, and an artist with more than 60 pages of releases (6000, more than anyone seen so far) is not checked this way and falls back to one lookup per row on screen, as before. Albums that none of the artist's releases belong to (for example a release credited to another artist) stay unchecked and keep the per-row lookups. A check that fails after three tries on a page says so with a Try again button, and keeps the pages it read for the next try. Progress is kept in memory only, so closing the app loses it. There is no "check all" button, no choosing more than one format, and the chosen format is not kept when you leave the artist.
- Opening hours use the phone's clock and time zone, so a shop in another time zone is judged by your local time. Public holidays are those of the region of the search area (a town, a place chosen from "Not the right place?", or your position), so a shop just over a border is judged by the wrong country's holidays. Holidays that depend on the shop's own town or religion are not known, and `SH` (school holidays) and other date rules make hours unreadable, so the raw text is shown. If Nager.Date cannot be reached and nothing is stored, the note that holidays may differ stays.
- The app has only been run on the emulator.
